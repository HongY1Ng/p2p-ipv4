# 设计文档：零基础设施 UDP 打洞工具

> 目标：**不需要任何服务器**，两端各跑一次，手工交换一行地址，建立直连通道。

---

## 一、目标与非目标

### 目标
- ✅ 零基础设施：不需要 VPS、不需要信令服务器、不需要注册
- ✅ 单文件、一键式：朋友下载后双击/一行命令就能跑
- ✅ 自带 NAT 探测：开跑前先知道自己这边的 NAT 类型
- ✅ 打通即用：成功后明确告诉用户"通道可用"并给出后续用法
- ✅ 失败要说清楚为什么失败（而不是干巴巴报个错）

### 非目标（明确不做）
- ❌ 中继兜底（打不通就是打不通，直接报错——这是刻意的设计取舍）
- ❌ 长期保活/开机自启（这是一次性建链工具，不是常驻服务）
- ❌ 图形界面（命令行足够）

---

## 二、⚠️ 关键修正：**单向上报是不够的**

最初的设想是：
```
A: 输出自己的公网地址 ──►  B: 输入 A 的地址，然后打洞
```

**这个流程只在一种情况下能成功**，原因是打洞的本质：

> 打洞 = **双方各自先向对方发一个包**，在**各自的 NAT** 上建立"允许对方回包"的规则。
> 只建立一边的规则，另一边照样丢包。

具体到"只有 B 打洞"的情况，包到达 A 的 NAT 时：

| A 的 NAT 过滤行为 | B 的包能否到达 A | 结果 |
|---|---|---|
| **EIF（全锥形）** | ✅ 放行 | 成功 |
| **地址受限锥形** | ❌ 丢弃（A 没给 B 发过包） | **失败** |
| **地址+端口受限锥形** | ❌ 丢弃 | **失败** |
| **对称型** | ❌ 丢弃 | **失败** |

**而国内家宽和蜂窝网络里，"全锥形"是少数。** 所以单向上报大概率打不通——但用户会以为是工具坏了。

### 修正：**双向交换**（只在必要时才需要第二步）

```
┌─ A 端 ────────────────────┐        ┌─ B 端 ────────────────────┐
│                           │        │                           │
│ 1. p2p advertise          │        │                           │
│    → 打印: 1.2.3.4:56789  │───────►│ 2. p2p connect 1.2.3.4:56789
│    (持续保活，等待)        │  人工   │    → 打印: 5.6.7.8:43210  │
│                           │  传递   │    → 开始持续向 A 发包     │
│ 3. 若 20 秒内没收到对方的   │◄───────│                           │
│    包 → 提示粘贴 B 的地址  │  人工   │                           │
│    → 双向同时打洞 ✅       │  传递   │                           │
└───────────────────────────┘        └───────────────────────────┘
```

**关键设计**：
- **如果 A 的 NAT 是全锥形** → B 的包直接到了 → A 自动学到 B 的地址并回包 → **只有第 1 步和第 2 步，一步到位** ✅
- **如果不是** → A 的脚本会提示"没收到对方的数据包，请把对方的地址也粘进来" → A 输入 B 的地址 → **双向同时打洞** ✅

**这样既保留了"能一步就一步"的简洁，又保证了"该两步时能成"。**

## 三、命令行界面设计

```
p2p probe                          探测本机 NAT 类型（可单独使用）
p2p advertise [--port N]           广播模式：打印自己的地址并等待对方
p2p connect <ip:port> [--port N]   连接模式：向对方打洞
```

两端**默认使用同一个本地端口（45678）**，可用 `--port` 改（两端必须一致）。

### 输出示例

**A 端：**
```
$ p2p advertise
[i] Probing NAT type ...  EIM (cone)
[i] Local port: 45678
[i] Keepalive started (every 15s)

==============================================
  Give this line to the other side:
==============================================

        1.2.3.4:56789

==============================================
  Waiting for peer (max 300s) ...
```

**B 端：**
```
$ p2p connect 1.2.3.4:56789
[i] Probing NAT type ...  EIM (cone)
[i] Local port: 45678
[i] Keepalive started (every 15s)

==============================================
  Give this line back to the other side:
==============================================

        5.6.7.8:43210

==============================================
  Punching to 1.2.3.4:56789 ...
```

**A 端（20 秒后如果还没收到对方的包）：**
```
[!] No packet received from peer after 20s.
    Your NAT is probably NOT full-cone.
    Paste the peer's address (from the other side) and press Enter:
    > 5.6.7.8:43210
[i] Punching to 5.6.7.8:43210 ...
```

**成功（两端都显示）：**
```
==============================================
  ✅ TUNNEL ESTABLISHED
==============================================
  Peer      : 5.6.7.8:43210
  RTT       : 23 ms  (min 21 / avg 24 / max 31)
  Loss      : 0%
  Local port: 45678

  The channel is now open. Next steps:
    - Bind your app to local port 45678 to use it
    - Or run WireGuard / QUIC on top of this socket
==============================================
```

**失败：**
```
==============================================
  ❌ PUNCHING FAILED
==============================================
  Tried for 60s, 0 packets received from peer.

  Likely causes:
    1. One side is behind SYMMETRIC NAT (run 'p2p probe' to check)
    2. One side is behind CGNAT with port randomisation
    3. Local firewall blocking inbound UDP on port 45678
    4. The two sides are on the same CGNAT and it lacks hairpinning

  This tool does NOT provide a relay fallback by design.
  Options:
    - Ask both sides to run 'p2p probe' and compare NAT types
    - If either side is symmetric, use a relay instead
==============================================
```

## 四、必须做对的几个技术点

| # | 要点 | 为什么 |
|---|---|---|
| 1 | **全程复用同一个 UDP socket** | NAT 映射绑定的是"内网 socket"。换 socket = 换端口 = 之前上报的地址失效 |
| 2 | **保活** | NAT 映射 30 秒~5 分钟就过期。人工传递地址要花时间，必须每 15~20 秒发个包撑住 |
| 3 | **双方同时发包** | 单向发包在受限锥形 NAT 上必失败（见第二节） |
| 4 | **持续重传，不是发一次** | 对方 NAT 上的规则建立需要时间差，首包通常会被丢 |
| 5 | **探测也走同一个 socket** | 探测得到的映射必须就是后面用来收包的映射 |
| 6 | **防火墙提示** | Windows 默认拦入站 UDP，第一次跑要提示用户放行 |

## 五、失败诊断（工具的核心价值之一）

失败时不要只报"失败"，要输出**可操作的信息**：

1. **两端的 NAT 类型**（自动探测并打印）
2. **收到了几个包**（0 个 = 对方根本没发过来 / 被中间设备丢；收到过但握手没完成 = 另一种问题）
3. **具体的排查建议**（按可能性排序）
4. **明确告知"本工具不提供中继"**，并给出替代方案

## 六、技术选型建议

| 方案 | 优点 | 缺点 |
|---|---|---|
| **Go** ⭐ 推荐 | 编译成**单文件 exe**，零依赖；跨平台（Win/Linux/macOS/ARM）；后续能上 QUIC 做数据面；GitHub Release 直接发二进制 | 需要装 Go 工具链（国内可用 `golang.google.cn` 镜像） |
| **PowerShell** | Windows 零安装；已有探测代码可复用 | `.ps1` 会被执行策略拦截，朋友体验差；无法跨平台；做不了 QUIC |
| Python | 写起来快 | 朋友要装 Python，违背"一键式" |

**推荐 Go**：这个工具是要发到 GitHub 让别人下载的，"下载一个 exe 双击就跑"是唯一能被普通人接受的形态。
